# Casebook — 나쁜 예 (Bad)

> routine이 매 실행 자기 채점으로 이 파일을 갱신한다(검증 패스에서 폐기된 사례,
> 재미 점수 2점 이하 등). **사람은 사례를 직접 작성하지 않고 거부권만 행사한다**
> (스펙 4.2). 아래 3건은 최초 시드 — 검증 패스가 반드시 걸러내야 하는 유형의 예시다.

## 1. 주관식 형태 (형식 위반)

```json
{
  "quizId": "QZ-BAD-001",
  "templateId": "YESTERDAY_WINNER",
  "format": "BINARY",
  "question": "어제 경기에서 가장 인상적인 장면은 무엇이었나요?",
  "options": [{ "id": "A", "text": "자유롭게 서술" }],
  "answer": null
}
```

**나쁜 이유**: `format: BINARY`라 선언했는데 실제 문제는 주관식(자유 서술)이고
`options`도 1개뿐이다 — 출제 형식 규칙(OX/BINARY 2개·MULTI4 4개, 즉시 판단 가능한
보기)을 완전히 벗어나 검증 패스 형식 검사(구 스펙 4.2 검증 4단계)에서 폐기된다.

## 2. evidence 없는 단정 (근거 없는 지식 퀴즈)

```json
{
  "quizId": "QZ-BAD-002",
  "templateId": "MEME_ORIGIN",
  "format": "MULTI4",
  "kind": "KNOWLEDGE",
  "question": "박병호의 별명 '홈런왕'의 유래는?",
  "options": [
    { "id": "A", "text": "2015년 시즌 53홈런으로 개인 최다 기록을 세워서" },
    { "id": "B", "text": "고교 시절부터 붙은 별명" },
    { "id": "C", "text": "은퇴 후 코치가 되면서 붙은 별명" },
    { "id": "D", "text": "팬들이 만든 응원가 제목" }
  ],
  "answer": "A",
  "evidence": {
    "source": "wiki/players/xxxxx.md#별명·밈",
    "quote": "박병호는 2015년 53홈런을 치며 리그 최고의 홈런타자로 자리매김했다."
  }
}
```

**나쁜 이유**: `evidence.quote`가 위키 원문을 그대로 인용한 게 아니라 LLM이
사실을 종합해 **창작**한 문장이다(생성 규칙 2번 위반) — 검증 패스 1단계가
`wiki/players/xxxxx.md`를 실제로 열어 이 문자열을 찾지 못하면 즉시 폐기된다.
근거를 찾지 못했다고 해서 그럴듯한 문장을 지어 채우면 안 된다.

## 3. 사건 언급 (안전 규칙 위반)

```json
{
  "quizId": "QZ-BAD-003",
  "templateId": "RELATION_LINK",
  "format": "MULTI4",
  "kind": "KNOWLEDGE",
  "question": "2023년 음주운전 사건으로 논란이 된 선수는?",
  "options": [
    { "id": "A", "text": "선수 A" },
    { "id": "B", "text": "선수 B" },
    { "id": "C", "text": "선수 C" },
    { "id": "D", "text": "선수 D" }
  ],
  "answer": "A",
  "evidence": { "source": "wiki/players/xxxxx.md#사건사고", "quote": "..." }
}
```

**나쁜 이유**: 위키의 `사건사고` 섹션을 정답 근거로 직접 인용했고, 질문 문구에
"음주운전"(banned-topics.txt 소재)까지 노출됐다 — 안전 규칙(사건사고·법적 논란
소재 출제 금지, 사건사고 섹션은 기록용일 뿐 퀴즈 소스 사용 금지)을 이중으로
위반한다. 결정적 키워드 필터(`validate_candidates.py`)와 검증 패스 3단계
(안전 재검) 양쪽에서 걸려야 정상이다.

## 사례: 범용 호칭 패턴을 고유 밈으로 착각 (2026-08-04, 사람 검수로 적발)

```json
{
  "templateId": "MEME_ORIGIN",
  "format": "MULTI4",
  "kind": "KNOWLEDGE",
  "question": "삼성 구자욱이 결정적 한 방을 쳤을 때 팬들이 부르는 존칭형 별명은?",
  "options": [
    { "id": "A", "text": "대자욱" },
    { "id": "B", "text": "구느님" },
    { "id": "C", "text": "왕자욱" },
    { "id": "D", "text": "갓자욱" }
  ],
  "answer": "A",
  "evidence": { "source": "wiki/players/62404.md#별명·밈", "quote": "대자욱: 결정적 한 방을 쳤을 때 팬들이 부르는 존칭형 별명" }
}
```

**나쁜 이유**: "대◯◯"는 잘한 선수 아무에게나 이름 앞에 "대"를 붙이는 **커뮤니티
공통 관용 패턴**이지 구자욱 고유의 밈이 아니다(사람 검수자 피드백 원문: "그냥
사람들이 보통 홈런 치거나 대단한 일 하면 이름 앞에 '대'를 붙여서 부르곤 하는데?
정답이 있는 밈이 아냐"). 같은 논리로 "갓◯◯"·"◯느님" 같은 오답 보기들도 현실에서
통용될 수 있어 **정답의 유일성이 성립하지 않는다**. evidence가 위키 원문과
일치하고 안전·중복 검사를 통과하더라도, **고유성 검사**(generation-rules §4-1,
verification-pass §3-1)에서 폐기해야 한다. 위키 `별명·밈` 섹션 수록은 커뮤니티
전언의 기록일 뿐 출제 적격의 보증이 아니다 — 출제 적격은 사람 승인 밈
시드(memes.yaml)가 보증한다.

## 4. evidence.source 경로 프리픽스 누락 (2026-08-12, 실행 중 자체 발견·수정)

```json
{
  "evidence": {
    "source": "game_result/2026-08-11/game_result_20260811KTNC02026.json",
    "quote": "2026-08-11 창원에서 열린 KT 대 NC 경기는 7:3, KT의 승리로 끝났다."
  }
}
```

**나쁜 이유**: quote 자체는 원문 그대로였지만(환각 아님), `source` 경로가
generation-rules.md §2 규칙("envelope 인용: `question-source/{docType}/{date}/
{doc_id}.json`")의 `question-source/` 프리픽스를 빠뜨렸다. `.work/`에 로컬
동기화된 실제 디스크 경로(`game_result/2026-08-11/...`)를 그대로 옮겨 적은
탓으로 보인다 — 로컬 캐시 경로와 evidence.source 계약 경로가 다르다는 점을
못 지켰다. `runner/finalize.py`의 `check_evidence`(경로 접두사로 대조 대상
파일을 결정)가 이 프리픽스를 기준으로 파일을 찾으므로, 빠지면 존재하는 파일도
못 찾아 대조 실패 → 정당한 후보가 폐기될 뻔했다(이번엔 실행 중 발견해 3건
직접 수정 후 재검증 통과). 다음 실행 문구 생성 시 `evidence.source`는 항상
`question-source/`·`wiki/` 로 시작하는 **계약 경로**를 쓰고, `.work/` 로컬
캐시의 실제 디스크 경로를 그대로 베끼지 않도록 주의할 것.

## 5. MEME_ORIGIN — 범용 호칭 패턴 재발 (2026-08-14, 검증 패스에서 폐기)

```json
{
  "templateId": "MEME_ORIGIN",
  "question": "삼성 이승민의 활약을 응원하는 팬들이 붙인 애칭은?",
  "options": [
    { "id": "A", "text": "대승민" }, { "id": "B", "text": "슈퍼승민" },
    { "id": "C", "text": "이승민 매직" }, { "id": "D", "text": "필승민" }
  ],
  "answer": "A",
  "evidence": {
    "source": "wiki/players/50464.md#별명·밈",
    "quote": "활약을 응원·치켜세우는 팬들이 붙인 애칭으로, \"대승민\"·\"대 대 대\" 등의 형태로 반복 등장한다"
  }
}
```

**나쁜 이유**: evidence는 위키 원문과 정확히 일치하지만 "대◯◯"는 §4-1이 명시적으로
막은 범용 호칭 패턴이다(2026-08-04 '대자욱' 사례와 동일 실패 모드) — 오답으로 쓴
"슈퍼승민"·"필승민"도 현실에서 다른 잘하는 선수에게 똑같이 붙을 수 있어 정답의
유일성이 성립하지 않는다. 위키 문서에 원문으로 존재한다는 사실이 출제 적격을
보증하지 않는다는 점이 두 달 뒤에도 반복되는 중 — 문구 생성 단계에서부터 "대◯◯"
패턴을 기계적으로도 걸러내는 사전 필터(정규식 등)를 추가하면 검증 패스까지 갈
필요 없이 더 일찍 차단할 수 있어 보인다(다음 실행 제안 사항).

## 6. CAREER_PATH — 데뷔팀=현재팀(서사 없는 동어반복) (2026-08-14, 검증 패스에서 폐기)

```json
{
  "templateId": "CAREER_PATH",
  "question": "두산 안재석이 프로 데뷔 시 1차 지명으로 입단한 팀은?",
  "options": [
    { "id": "A", "text": "두산" }, { "id": "B", "text": "LG" },
    { "id": "C", "text": "삼성" }, { "id": "D", "text": "KT" }
  ],
  "answer": "A",
  "evidence": {
    "source": "wiki/players/51203.md#커리어 이력",
    "quote": "2021년 두산 베어스에 1차 지명으로 입단했다"
  }
}
```

**나쁜 이유**: 안재석은 데뷔 이후 팀을 옮긴 적이 없어 "입단 팀"이 곧 "현재 소속팀"과
같다 — 오늘 이 문항이 실릴 경기 묶음 자체가 "두산 대 KIA"이므로 팬이 굳이 몰라도
맞힐 수 있는 사실상 정답 유출에 가깝다. CAREER_PATH의 의도("선수가 거쳐간 팀
순서")는 실제로 이적 이력이 있는 선수에게만 의미가 있다 — 후보 선정 시 evidence
문장에 "트레이드"·"FA"·"이적" 등 실제 팀 이동을 가리키는 표현이 있는지 먼저 걸러야
한다(§33의 성공 사례 '페덱'과 대비: 그쪽은 실제 다구단 경쟁이라는 서사가 있었다).

## 7. HOME_AWAY_SPLIT — 격차가 통계적으로 무의미한 수준 (2026-08-14, 검증 패스에서 폐기)

```json
{
  "templateId": "HOME_AWAY_SPLIT",
  "question": "SSG는 홈과 원정 중 어느 쪽 성적이 더 좋을까?",
  "options": [{ "id": "A", "text": "홈" }, { "id": "B", "text": "원정" }],
  "answer": "A",
  "evidence": { "source": "wiki/stats/season.md#홈/원정", "quote": "| SK | 21-29-3 | 20-32-1 |" }
}
```

**나쁜 이유**: 홈 승률(21승29패3무 ≈ .420)과 원정 승률(20승32패1무 ≈ .385)의
차이가 약 3.5%p — 카탈로그 intent가 명시한 "격차 큰 팀 선호"를 지키지 않은
채 생성됐다. SK-LG 경기 묶음과 NC-LT 경기 묶음 양쪽에서 각자 다른 팀(SK, NC)에
대해 같은 실패 패턴(격차 1~4%p대)이 독립적으로 발생했다 — 우연이 아니라 여러
팀의 홈/원정 성적이 원래 비슷비슷하기 쉽다는 신호로 보인다. 문구 생성 단계에서
"격차 ≥ 10%p(또는 승패 5경기 이상 차이)"처럼 기계적으로 확인 가능한 최소 기준을
먼저 걸러야 검증 패스까지 갈 필요 없이 더 일찍 차단할 수 있다(다음 실행 제안).

## 8. RELATION_LINK — 같은 사실을 다른 멤버 조합·다른 근거로 재탕 (2026-08-14, 검증 패스에서 폐기)

**나쁜 이유** (OB-HT 경기 묶음 사례, 예시 JSON 생략): "김민석|김대한" 페어로 만든
RELATION_LINK 문항이 evidence·형식 모두 문제없었지만, 안재석·박준순까지 포함한
4인 그룹("머갈툴순")의 소속 사실을 **멤버 조합만 바꿔가며** 이미 이틀 연속
(`QZ-20260811-054`, `QZ-20260812-027`) 물었던 사실이라 폐기됐다. 같은 날 WO-KT
경기 묶음에서도 유일한 RELATION_LINK 후보(임지열|이형종)가 2026-08-12에 **완전히
동일한 evidence 인용문**으로 이미 발행된 적이 있어 폐기됐다. 중복 검사는 페어의
문자열 동일성만이 아니라 "근거가 되는 근본 사실(그룹 소속·관계)"까지 봐야 한다 —
멤버 조합을 바꾸는 것은 새로운 사실이 아니라 같은 사실의 다른 부분집합일 뿐이다.

## 9. YESTERDAY_SCORE — 정답 보기 문면에 팀명을 그대로 써서 정답 유출 (2026-08-15, `validate_candidates.py` 게이트에서 폐기)

```json
{
  "templateId": "YESTERDAY_SCORE",
  "question": "어제(8/14) NC vs 롯데 최종 스코어는?",
  "options": [
    { "id": "A", "text": "NC 9 - 롯데 8" }, { "id": "B", "text": "NC 8 - 롯데 9" },
    { "id": "C", "text": "NC 7 - 롯데 8" }, { "id": "D", "text": "NC 9 - 롯데 6" }
  ],
  "answer": "A",
  "subject": { "scope": "GAME", "teamCodes": ["NC", "LT"] }
}
```

**나쁜 이유**: scope=GAME이고 스코어형이라 §11 규칙대로 `subject.teamCodes`에
양 팀을 담은 것 자체는 맞았지만, 보기 문면을 "NC 9 - 롯데 8"처럼 팀 이름을 넣어
써서 `validate_candidates.py` check 9(정답 유출)에 걸렸다. 같은 실행의 다른 4개
경기 묶음은 전부 "9:8"처럼 팀명 없이 스코어만 쓰는 형식을 썼는데 이 한 묶음만
형식이 어긋났다 — §11이 명시하는 "스코어형은 팀을 다 담는다"는 **subject
필드** 얘기지 **보기 문구에 팀 이름을 적으라는 뜻이 아니다**. 문구 생성 규칙에
"스코어형 보기는 숫자만(팀명 금지)"이라고 명시적으로 못박을 필요가 있다(다음
실행 제안). 최종 채택 직전 게이트에서 잡혀 업로드 직전에 수동으로 고쳐 살렸다.

## 10. RELATION_LINK — 경기 묶음당 EXPERT 재료가 구조적으로 얇음 (2026-08-15, 3개 경기 묶음에서 반복 관측)

**나쁜 이유** (예시 JSON 생략, 여러 묶음에서 공통 관측): NC-LT·HH-SS·WO-KT·SK-LG
네 경기 묶음 중 셋(NC-LT는 아예 0건, HH-SS·WO-KT·SK-LG는 유일한 후보가 최근 7일
중복으로 폐기)에서 그날 경기 양 팀 소속 선수만 잇는 안전 그래프 엣지(밈공유·
커리어교차·라이벌)가 1건 이하였다. scoring.yaml 조정 이력 주석의 "EXPERT 실측
충족 0~1"이 팀 조합을 가리지 않고 광범위하게 재현된다는 뜻이다 — 이 문제는
데이터가 쌓이면 자연히 풀리지만(위키 빌더가 관계 엣지를 계속 축적 중), 그 전까지
경기 묶음의 EXPERT 1슬롯은 구조적으로 자주 빈다는 걸 전제하고 봐야 한다.

## 11. MEME_OWNER — "-신"·"-맘" 애정 접미사, 비하 어감 표현 재확인 (2026-08-15, 공통 묶음에서 생성 단계 자체 폐기)

## 17. RELATION_LINK — wiki 원문은 진짜인데 graph.json 엣지가 없는 사고 (2026-08-19 실행)

2026-08-19 실행은 경기 문항을 병렬 서브에이전트 5개로 나눠 생성했다. OB-NC
담당 에이전트가 번들에 미리 계산해 둔 그래프 쌍 8개가 전부 최근 7일 중복으로
막히자, 스스로 wiki 문서를 훑어 다음 후보를 만들어 제출했다:

```json
{
  "tempId": "T13",
  "templateId": "RELATION_LINK",
  "question": "두산 팬들이 박신지·윤태호 등판을 보면 나오는 드립은?",
  "answer": "A",
  "evidence": { "source": "wiki/players/52202.md#별명·밈",
    "quote": "두 투수가 큰 점수 차 경기에서만 기용된다는 이유로 왜 등판시키지 않냐는 질문과 놀림이 반복되는 커뮤니티 밈이다..." },
  "subject": { "scope": "PLAYER", "playerIds": [52202, 68249], "teamCodes": [], "gameId": null }
}
```

evidence quote는 실제로 `wiki/players/52202.md`에 원문 그대로 존재했고(에이전트의
자체 원문 대조도 통과), 두 선수가 진짜로 같은 밈을 공유한다는 서술도 사실이다.
그런데도 이 후보는 오케스트레이터의 집계 단계에서 최종 폐기됐다 — `graph.json`을
직접 열어 대조해 보니 52202↔68249 사이에는 `소속`(team 소속) 엣지만 있고
`밈공유`/`커리어교차`/`라이벌` 엣지가 **하나도 없었다**(두 선수의 `relations`
frontmatter도 둘 다 빈 배열).

**나쁜 이유**: `RELATION_LINK`의 `needs: [graph, wiki]`는 "관계가 graph.json에
결정적으로 등재된 쌍만 쓴다"는 계약이다(`runner/binding.py`의 `_graph_pairs`가
그 등재 여부로 후보 엔티티를 결정적으로 열거한다). wiki 원문에 관계가 서술돼
있다는 사실만으로는 이 계약을 충족하지 못한다 — 한 선수 문서의 "별명·밈" 절이
다른 선수를 언급한다고 해서 그게 자동으로 graph 엣지가 되는 것은 아니다(그래프
빌더가 아직 그 관계를 엣지로 등재하지 않았을 수 있다). evidence 원문 대조를
통과했다는 사실이 "이 템플릿의 데이터 출처 계약을 지켰다"는 것과 별개라는 게
이번 사고의 핵심이다 — 검증 패스 §1(evidence 원문 대조)만으로는 이런 종류의
결함을 못 잡는다.

**규칙**: `RELATION_LINK` 후보를 만들 때는 (a) evidence quote 원문 대조뿐 아니라
(b) 그 두 선수 쌍이 `graph.json`의 `edges`에 `type`이 밈공유/커리어교차/라이벌인
엣지로 **실제로 존재하는지**를 별도로 확인한다. 번들에 미리 계산된 그래프 쌍
목록이 전부 소진됐다면, wiki 원문에서 관계를 "발견"해 새 쌍을 즉석에서 만들지
말고 그 실행에서는 RELATION_LINK를 건너뛴다(다른 EXPERT 재료가 없다면 EXPERT
슬롯 미달로 두는 편이 낫다 — scoring.yaml 주석의 "재료 상한" 문서화 사례와 같은
패턴).
