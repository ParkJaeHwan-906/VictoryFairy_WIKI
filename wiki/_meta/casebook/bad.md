# Casebook — 나쁜 예 (Bad)

> routine이 매 실행 자기 채점으로 이 파일을 갱신한다(검증 패스에서 폐기된 사례,
> 재미 점수 2점 이하 등). **사람은 사례를 직접 작성하지 않고 거부권만 행사한다**
> (스펙 4.2). 아래 3건은 최초 시드 — 검증 패스가 반드시 걸러내야 하는 유형의 예시다.

## 1. 주관식 형태 (형식 위반)

```json
{
  "quizId": "QZ-BAD-001",
  "templateId": "YESTERDAY_WINNER",
  "format": "BINARY",
  "question": "어제 경기에서 가장 인상적인 장면은 무엇이었나요?",
  "options": [{ "id": "A", "text": "자유롭게 서술" }],
  "answer": null
}
```

**나쁜 이유**: `format: BINARY`라 선언했는데 실제 문제는 주관식(자유 서술)이고
`options`도 1개뿐이다 — 출제 형식 규칙(OX/BINARY 2개·MULTI4 4개, 즉시 판단 가능한
보기)을 완전히 벗어나 검증 패스 형식 검사(구 스펙 4.2 검증 4단계)에서 폐기된다.

## 2. evidence 없는 단정 (근거 없는 지식 퀴즈)

```json
{
  "quizId": "QZ-BAD-002",
  "templateId": "MEME_ORIGIN",
  "format": "MULTI4",
  "kind": "KNOWLEDGE",
  "question": "박병호의 별명 '홈런왕'의 유래는?",
  "options": [
    { "id": "A", "text": "2015년 시즌 53홈런으로 개인 최다 기록을 세워서" },
    { "id": "B", "text": "고교 시절부터 붙은 별명" },
    { "id": "C", "text": "은퇴 후 코치가 되면서 붙은 별명" },
    { "id": "D", "text": "팬들이 만든 응원가 제목" }
  ],
  "answer": "A",
  "evidence": {
    "source": "wiki/players/xxxxx.md#별명·밈",
    "quote": "박병호는 2015년 53홈런을 치며 리그 최고의 홈런타자로 자리매김했다."
  }
}
```

**나쁜 이유**: `evidence.quote`가 위키 원문을 그대로 인용한 게 아니라 LLM이
사실을 종합해 **창작**한 문장이다(생성 규칙 2번 위반) — 검증 패스 1단계가
`wiki/players/xxxxx.md`를 실제로 열어 이 문자열을 찾지 못하면 즉시 폐기된다.
근거를 찾지 못했다고 해서 그럴듯한 문장을 지어 채우면 안 된다.

## 3. 사건 언급 (안전 규칙 위반)

```json
{
  "quizId": "QZ-BAD-003",
  "templateId": "RELATION_LINK",
  "format": "MULTI4",
  "kind": "KNOWLEDGE",
  "question": "2023년 음주운전 사건으로 논란이 된 선수는?",
  "options": [
    { "id": "A", "text": "선수 A" },
    { "id": "B", "text": "선수 B" },
    { "id": "C", "text": "선수 C" },
    { "id": "D", "text": "선수 D" }
  ],
  "answer": "A",
  "evidence": { "source": "wiki/players/xxxxx.md#사건사고", "quote": "..." }
}
```

**나쁜 이유**: 위키의 `사건사고` 섹션을 정답 근거로 직접 인용했고, 질문 문구에
"음주운전"(banned-topics.txt 소재)까지 노출됐다 — 안전 규칙(사건사고·법적 논란
소재 출제 금지, 사건사고 섹션은 기록용일 뿐 퀴즈 소스 사용 금지)을 이중으로
위반한다. 결정적 키워드 필터(`validate_candidates.py`)와 검증 패스 3단계
(안전 재검) 양쪽에서 걸려야 정상이다.

## 사례: 범용 호칭 패턴을 고유 밈으로 착각 (2026-08-04, 사람 검수로 적발)

```json
{
  "templateId": "MEME_ORIGIN",
  "format": "MULTI4",
  "kind": "KNOWLEDGE",
  "question": "삼성 구자욱이 결정적 한 방을 쳤을 때 팬들이 부르는 존칭형 별명은?",
  "options": [
    { "id": "A", "text": "대자욱" },
    { "id": "B", "text": "구느님" },
    { "id": "C", "text": "왕자욱" },
    { "id": "D", "text": "갓자욱" }
  ],
  "answer": "A",
  "evidence": { "source": "wiki/players/62404.md#별명·밈", "quote": "대자욱: 결정적 한 방을 쳤을 때 팬들이 부르는 존칭형 별명" }
}
```

**나쁜 이유**: "대◯◯"는 잘한 선수 아무에게나 이름 앞에 "대"를 붙이는 **커뮤니티
공통 관용 패턴**이지 구자욱 고유의 밈이 아니다(사람 검수자 피드백 원문: "그냥
사람들이 보통 홈런 치거나 대단한 일 하면 이름 앞에 '대'를 붙여서 부르곤 하는데?
정답이 있는 밈이 아냐"). 같은 논리로 "갓◯◯"·"◯느님" 같은 오답 보기들도 현실에서
통용될 수 있어 **정답의 유일성이 성립하지 않는다**. evidence가 위키 원문과
일치하고 안전·중복 검사를 통과하더라도, **고유성 검사**(generation-rules §4-1,
verification-pass §3-1)에서 폐기해야 한다. 위키 `별명·밈` 섹션 수록은 커뮤니티
전언의 기록일 뿐 출제 적격의 보증이 아니다 — 출제 적격은 사람 승인 밈
시드(memes.yaml)가 보증한다.

## 4. evidence.source 경로 프리픽스 누락 (2026-08-12, 실행 중 자체 발견·수정)

```json
{
  "evidence": {
    "source": "game_result/2026-08-11/game_result_20260811KTNC02026.json",
    "quote": "2026-08-11 창원에서 열린 KT 대 NC 경기는 7:3, KT의 승리로 끝났다."
  }
}
```

**나쁜 이유**: quote 자체는 원문 그대로였지만(환각 아님), `source` 경로가
generation-rules.md §2 규칙("envelope 인용: `question-source/{docType}/{date}/
{doc_id}.json`")의 `question-source/` 프리픽스를 빠뜨렸다. `.work/`에 로컬
동기화된 실제 디스크 경로(`game_result/2026-08-11/...`)를 그대로 옮겨 적은
탓으로 보인다 — 로컬 캐시 경로와 evidence.source 계약 경로가 다르다는 점을
못 지켰다. `runner/finalize.py`의 `check_evidence`(경로 접두사로 대조 대상
파일을 결정)가 이 프리픽스를 기준으로 파일을 찾으므로, 빠지면 존재하는 파일도
못 찾아 대조 실패 → 정당한 후보가 폐기될 뻔했다(이번엔 실행 중 발견해 3건
직접 수정 후 재검증 통과). 다음 실행 문구 생성 시 `evidence.source`는 항상
`question-source/`·`wiki/` 로 시작하는 **계약 경로**를 쓰고, `.work/` 로컬
캐시의 실제 디스크 경로를 그대로 베끼지 않도록 주의할 것.

## 5. MEME_ORIGIN — 범용 호칭 패턴 재발 (2026-08-14, 검증 패스에서 폐기)

```json
{
  "templateId": "MEME_ORIGIN",
  "question": "삼성 이승민의 활약을 응원하는 팬들이 붙인 애칭은?",
  "options": [
    { "id": "A", "text": "대승민" }, { "id": "B", "text": "슈퍼승민" },
    { "id": "C", "text": "이승민 매직" }, { "id": "D", "text": "필승민" }
  ],
  "answer": "A",
  "evidence": {
    "source": "wiki/players/50464.md#별명·밈",
    "quote": "활약을 응원·치켜세우는 팬들이 붙인 애칭으로, \"대승민\"·\"대 대 대\" 등의 형태로 반복 등장한다"
  }
}
```

**나쁜 이유**: evidence는 위키 원문과 정확히 일치하지만 "대◯◯"는 §4-1이 명시적으로
막은 범용 호칭 패턴이다(2026-08-04 '대자욱' 사례와 동일 실패 모드) — 오답으로 쓴
"슈퍼승민"·"필승민"도 현실에서 다른 잘하는 선수에게 똑같이 붙을 수 있어 정답의
유일성이 성립하지 않는다. 위키 문서에 원문으로 존재한다는 사실이 출제 적격을
보증하지 않는다는 점이 두 달 뒤에도 반복되는 중 — 문구 생성 단계에서부터 "대◯◯"
패턴을 기계적으로도 걸러내는 사전 필터(정규식 등)를 추가하면 검증 패스까지 갈
필요 없이 더 일찍 차단할 수 있어 보인다(다음 실행 제안 사항).

## 6. CAREER_PATH — 데뷔팀=현재팀(서사 없는 동어반복) (2026-08-14, 검증 패스에서 폐기)

```json
{
  "templateId": "CAREER_PATH",
  "question": "두산 안재석이 프로 데뷔 시 1차 지명으로 입단한 팀은?",
  "options": [
    { "id": "A", "text": "두산" }, { "id": "B", "text": "LG" },
    { "id": "C", "text": "삼성" }, { "id": "D", "text": "KT" }
  ],
  "answer": "A",
  "evidence": {
    "source": "wiki/players/51203.md#커리어 이력",
    "quote": "2021년 두산 베어스에 1차 지명으로 입단했다"
  }
}
```

**나쁜 이유**: 안재석은 데뷔 이후 팀을 옮긴 적이 없어 "입단 팀"이 곧 "현재 소속팀"과
같다 — 오늘 이 문항이 실릴 경기 묶음 자체가 "두산 대 KIA"이므로 팬이 굳이 몰라도
맞힐 수 있는 사실상 정답 유출에 가깝다. CAREER_PATH의 의도("선수가 거쳐간 팀
순서")는 실제로 이적 이력이 있는 선수에게만 의미가 있다 — 후보 선정 시 evidence
문장에 "트레이드"·"FA"·"이적" 등 실제 팀 이동을 가리키는 표현이 있는지 먼저 걸러야
한다(§33의 성공 사례 '페덱'과 대비: 그쪽은 실제 다구단 경쟁이라는 서사가 있었다).

## 7. HOME_AWAY_SPLIT — 격차가 통계적으로 무의미한 수준 (2026-08-14, 검증 패스에서 폐기)

```json
{
  "templateId": "HOME_AWAY_SPLIT",
  "question": "SSG는 홈과 원정 중 어느 쪽 성적이 더 좋을까?",
  "options": [{ "id": "A", "text": "홈" }, { "id": "B", "text": "원정" }],
  "answer": "A",
  "evidence": { "source": "wiki/stats/season.md#홈/원정", "quote": "| SK | 21-29-3 | 20-32-1 |" }
}
```

**나쁜 이유**: 홈 승률(21승29패3무 ≈ .420)과 원정 승률(20승32패1무 ≈ .385)의
차이가 약 3.5%p — 카탈로그 intent가 명시한 "격차 큰 팀 선호"를 지키지 않은
채 생성됐다. SK-LG 경기 묶음과 NC-LT 경기 묶음 양쪽에서 각자 다른 팀(SK, NC)에
대해 같은 실패 패턴(격차 1~4%p대)이 독립적으로 발생했다 — 우연이 아니라 여러
팀의 홈/원정 성적이 원래 비슷비슷하기 쉽다는 신호로 보인다. 문구 생성 단계에서
"격차 ≥ 10%p(또는 승패 5경기 이상 차이)"처럼 기계적으로 확인 가능한 최소 기준을
먼저 걸러야 검증 패스까지 갈 필요 없이 더 일찍 차단할 수 있다(다음 실행 제안).

## 8. RELATION_LINK — 같은 사실을 다른 멤버 조합·다른 근거로 재탕 (2026-08-14, 검증 패스에서 폐기)

**나쁜 이유** (OB-HT 경기 묶음 사례, 예시 JSON 생략): "김민석|김대한" 페어로 만든
RELATION_LINK 문항이 evidence·형식 모두 문제없었지만, 안재석·박준순까지 포함한
4인 그룹("머갈툴순")의 소속 사실을 **멤버 조합만 바꿔가며** 이미 이틀 연속
(`QZ-20260811-054`, `QZ-20260812-027`) 물었던 사실이라 폐기됐다. 같은 날 WO-KT
경기 묶음에서도 유일한 RELATION_LINK 후보(임지열|이형종)가 2026-08-12에 **완전히
동일한 evidence 인용문**으로 이미 발행된 적이 있어 폐기됐다. 중복 검사는 페어의
문자열 동일성만이 아니라 "근거가 되는 근본 사실(그룹 소속·관계)"까지 봐야 한다 —
멤버 조합을 바꾸는 것은 새로운 사실이 아니라 같은 사실의 다른 부분집합일 뿐이다.

## 9. YESTERDAY_SCORE — 정답 보기 문면에 팀명을 그대로 써서 정답 유출 (2026-08-15, `validate_candidates.py` 게이트에서 폐기)

```json
{
  "templateId": "YESTERDAY_SCORE",
  "question": "어제(8/14) NC vs 롯데 최종 스코어는?",
  "options": [
    { "id": "A", "text": "NC 9 - 롯데 8" }, { "id": "B", "text": "NC 8 - 롯데 9" },
    { "id": "C", "text": "NC 7 - 롯데 8" }, { "id": "D", "text": "NC 9 - 롯데 6" }
  ],
  "answer": "A",
  "subject": { "scope": "GAME", "teamCodes": ["NC", "LT"] }
}
```

**나쁜 이유**: scope=GAME이고 스코어형이라 §11 규칙대로 `subject.teamCodes`에
양 팀을 담은 것 자체는 맞았지만, 보기 문면을 "NC 9 - 롯데 8"처럼 팀 이름을 넣어
써서 `validate_candidates.py` check 9(정답 유출)에 걸렸다. 같은 실행의 다른 4개
경기 묶음은 전부 "9:8"처럼 팀명 없이 스코어만 쓰는 형식을 썼는데 이 한 묶음만
형식이 어긋났다 — §11이 명시하는 "스코어형은 팀을 다 담는다"는 **subject
필드** 얘기지 **보기 문구에 팀 이름을 적으라는 뜻이 아니다**. 문구 생성 규칙에
"스코어형 보기는 숫자만(팀명 금지)"이라고 명시적으로 못박을 필요가 있다(다음
실행 제안). 최종 채택 직전 게이트에서 잡혀 업로드 직전에 수동으로 고쳐 살렸다.

## 10. RELATION_LINK — 경기 묶음당 EXPERT 재료가 구조적으로 얇음 (2026-08-15, 3개 경기 묶음에서 반복 관측)

**나쁜 이유** (예시 JSON 생략, 여러 묶음에서 공통 관측): NC-LT·HH-SS·WO-KT·SK-LG
네 경기 묶음 중 셋(NC-LT는 아예 0건, HH-SS·WO-KT·SK-LG는 유일한 후보가 최근 7일
중복으로 폐기)에서 그날 경기 양 팀 소속 선수만 잇는 안전 그래프 엣지(밈공유·
커리어교차·라이벌)가 1건 이하였다. scoring.yaml 조정 이력 주석의 "EXPERT 실측
충족 0~1"이 팀 조합을 가리지 않고 광범위하게 재현된다는 뜻이다 — 이 문제는
데이터가 쌓이면 자연히 풀리지만(위키 빌더가 관계 엣지를 계속 축적 중), 그 전까지
경기 묶음의 EXPERT 1슬롯은 구조적으로 자주 빈다는 걸 전제하고 봐야 한다.

## 11. MEME_OWNER — "-신"·"-맘" 애정 접미사, 비하 어감 표현 재확인 (2026-08-15, 공통 묶음에서 생성 단계 자체 폐기)

## 17. RELATION_LINK — wiki 원문은 진짜인데 graph.json 엣지가 없는 사고 (2026-08-19 실행)

2026-08-19 실행은 경기 문항을 병렬 서브에이전트 5개로 나눠 생성했다. OB-NC
담당 에이전트가 번들에 미리 계산해 둔 그래프 쌍 8개가 전부 최근 7일 중복으로
막히자, 스스로 wiki 문서를 훑어 다음 후보를 만들어 제출했다:

```json
{
  "tempId": "T13",
  "templateId": "RELATION_LINK",
  "question": "두산 팬들이 박신지·윤태호 등판을 보면 나오는 드립은?",
  "answer": "A",
  "evidence": { "source": "wiki/players/52202.md#별명·밈",
    "quote": "두 투수가 큰 점수 차 경기에서만 기용된다는 이유로 왜 등판시키지 않냐는 질문과 놀림이 반복되는 커뮤니티 밈이다..." },
  "subject": { "scope": "PLAYER", "playerIds": [52202, 68249], "teamCodes": [], "gameId": null }
}
```

evidence quote는 실제로 `wiki/players/52202.md`에 원문 그대로 존재했고(에이전트의
자체 원문 대조도 통과), 두 선수가 진짜로 같은 밈을 공유한다는 서술도 사실이다.
그런데도 이 후보는 오케스트레이터의 집계 단계에서 최종 폐기됐다 — `graph.json`을
직접 열어 대조해 보니 52202↔68249 사이에는 `소속`(team 소속) 엣지만 있고
`밈공유`/`커리어교차`/`라이벌` 엣지가 **하나도 없었다**(두 선수의 `relations`
frontmatter도 둘 다 빈 배열).

**나쁜 이유**: `RELATION_LINK`의 `needs: [graph, wiki]`는 "관계가 graph.json에
결정적으로 등재된 쌍만 쓴다"는 계약이다(`runner/binding.py`의 `_graph_pairs`가
그 등재 여부로 후보 엔티티를 결정적으로 열거한다). wiki 원문에 관계가 서술돼
있다는 사실만으로는 이 계약을 충족하지 못한다 — 한 선수 문서의 "별명·밈" 절이
다른 선수를 언급한다고 해서 그게 자동으로 graph 엣지가 되는 것은 아니다(그래프
빌더가 아직 그 관계를 엣지로 등재하지 않았을 수 있다). evidence 원문 대조를
통과했다는 사실이 "이 템플릿의 데이터 출처 계약을 지켰다"는 것과 별개라는 게
이번 사고의 핵심이다 — 검증 패스 §1(evidence 원문 대조)만으로는 이런 종류의
결함을 못 잡는다.

**규칙**: `RELATION_LINK` 후보를 만들 때는 (a) evidence quote 원문 대조뿐 아니라
(b) 그 두 선수 쌍이 `graph.json`의 `edges`에 `type`이 밈공유/커리어교차/라이벌인
엣지로 **실제로 존재하는지**를 별도로 확인한다. 번들에 미리 계산된 그래프 쌍
목록이 전부 소진됐다면, wiki 원문에서 관계를 "발견"해 새 쌍을 즉석에서 만들지
말고 그 실행에서는 RELATION_LINK를 건너뛴다(다른 EXPERT 재료가 없다면 EXPERT
슬롯 미달로 두는 편이 낫다 — scoring.yaml 주석의 "재료 상한" 문서화 사례와 같은
패턴).

## 18. HOME_AWAY_SPLIT — 격차가 통계적으로 무의미한 팀에도 "어느 쪽이 강한가"를 단정해 물음 (2026-08-21 실행, KT-SK 묶음)

```json

  "question": "KT는 홈과 원정 중 어느 쪽 성적이 더 좋을까?",
  "options": [{ "id": "A", "text": "홈" }, { "id": "B", "text": "원정" }],
  "answer": "A",
  "evidence": { "source": "wiki/stats/season.md#홈/원정",
    "quote": "| KT | 31-20-1 | 32-21-1 |" },
  "difficulty": "MEDIUM"

```

같은 묶음의 SK 버전도 홈 21승29패3무 vs 원정 24승34패1무로 마찬가지였다.
검증 패스가 승률을 직접 계산해보니 KT는 홈 .608 vs 원정 .604(격차 0.4%p),

**나쁜 이유**: evidence 원문 대조도 통과하고 카탈로그 계약(§11 subjectScope=TEAM)도

사실상 동전 던지기와 다르지 않은데 문항은 마치 뚜렷한 경향이 있는 것처럼
단정한다 — evidence가 "원문 그대로"라는 사실이 "그 사실이 흥미롭거나 유의미하다"는
것을 보장하지 않는다는 §4 재미 채점의 존재 이유를 보여주는 사례다.

**규칙**: `HOME_AWAY_SPLIT`·`RECENT_VS_EARLY`처럼 두 구간을 비교해 우열을 묻는
템플릿은 문구를 쓰기 전에 실제 격차부터 계산해본다(생성 규칙 §5 "지나치게 쉽거나
어려우면 재분류" 원칙의 연장 — 격차가 근소하면 재분류가 아니라 그 팀은 스킵하는
게 맞다). generation-rules.md는 수치 계산을 LLM에 금지하므로, 이 판단은 검증
패스가 `season.md` 표의 숫자를 직접 대조해서 내려야 한다(사람이 보기에도 격차가
있는지 눈대중하지 말고 승률 차이를 실제로 빼볼 것).

## 20. CAREER_PATH — evidence에 없는 인과관계("FA 이적")를 질문 문구가 단정 (2026-08-21 실행, KT-SK 묶음)

검증 패스가 이 evidence 원문과 위키 문서 전체를 다시 읽어보니, "삼성 소속
시절 통산 득점 순위 5위"라는 기록 사실만 있을 뿐 **"FA로 이적했다"는 서술은

**나쁜 이유**: evidence.quote는 원문 그대로라 §1 대조는 통과하지만, **질문

전체가 evidence로 뒷받침되는가"까지는 확인하지 못한다는 맹점을 보여준다.
"~로 이적하기 전" 같은 인과·경위 서술은 그 자체가 별도의 사실 주장이므로
evidence에 그 표현이 명시돼 있어야 한다.

**규칙**: CAREER_PATH처럼 "왜/어떻게 팀을 옮겼는지"를 서술하는 템플릿은 질문에
이적 사유(트레이드/FA/방출 등)를 넣기 전에 evidence quote 안에 그 사유가
명시돼 있는지 별도로 확인한다. 원문에 "~시절"·"~소속" 같은 단순 소속 사실만
있다면 질문도 "김상수가 KT 이전에 오래 뛴 팀은?"처럼 이적 사유를 특정하지 않는
중립적 문구로 쓴다.

  살아남은 건 격차가 유난히 커서 최근에 안 쓰였던 HH·HT 둘뿐.
- `STREAK_CURRENT`: "1연승"·"1연패"처럼 **길이가 1인 연속 기록**은 팀이 매일 갱신되는
  값인데도 다른 팀에서 거의 매일 발생하는 흔한 값이라, 최근 7일 안에 "- XX: 1연패"
  형태의 동일 quote가 이미 등장했을 확률이 높다 — 오늘도 SK·OB·KT 3개가 이 이유로
  폐기됐다(2연승·2연패처럼 길이가 2 이상인 값은 전부 살아남았다).
- `CAREER_PATH`: 트레이드·데뷔팀처럼 완전히 정적인 사실은 그 선수를 다시 쓰면 반드시
  중복이다 — 한재승(KIA)·박세혁(삼성)의 트레이드 사실이 최근 7일 안에 이미 같은
  quote로 나와 있어 오늘 몫에서 빠졌다.
- `ALL_TIME_LEADER`(역대 타율 top-hitter, true-rank 10개 항목)는 최근 7일 누적으로
  **10개 순위 전부**가 이미 한 번씩 쓰였다 — 애초에 계획한 rank 1·5는 생성 단계에서
  바로 걸릴 걸 알고 rank 2·4로 바꿔 냈다. `MILESTONE_FIRST`·`RECORD_OX`도 같은
  all-time-records 풀(30항목)을 나눠 쓰다 보니 절반 이상이 이미 소진된 상태였다.

**대응**: 생성 단계에서 최근 7일 quote 집합을 미리 대조해 가능한 만큼 신선한 항목으로
바꿔 냈다(all-time-records 3개 템플릿, STANDINGS_CLIMB 2개, MONTHLY_BEST 1개,
MEME_OWNER 1개는 이렇게 선제 교체). 다만 `HOME_AWAY_SPLIT`·`STREAK_CURRENT`(길이 1)·
`CAREER_PATH`처럼 후보 자체가 팀당 1~2개뿐이라 바꿔 낼 여지가 없는 템플릿은 검증
단계에서 그대로 폐기됐다 — 경기가 있는 날이라도 "정적 사실 + 좁은 엔티티 폭" 조합은
매일 안정적으로 채우기 어렵다는 뜻이다.

**제안**: `STREAK_CURRENT`는 길이가 1인 값(가장 흔한 경우)을 아예 후보에서 빼거나,
그런 날은 다른 팀으로 대체할 여지를 만드는 게 낫다 — 지금은 팀별로 후보를 1개씩만
만들어 대체 수단이 없다. `HOME_AWAY_SPLIT`도 매일 내는 대신 격차가 큰 팀 목록을
순환시켜 격일로 내는 편이 중복 폐기율을 줄일 것이다.

## 29. 대진 반복(어제=오늘 동일 매치업)으로 MATCHUP 템플릿 전멸 (2026-08-26 실행)

오늘 5경기(HH-SK·LT-HT·NC-LG·OB-KT·SS-WO)가 **어제(8/25)와 정확히 같은 대진**이었다
— 우천 연기 후 이틀 연속 편성 등으로 보인다. 이 때문에 `H2H_SEASON_RECORD`·
`LAST_MATCHUP` 두 템플릿을 5경기 전부에서 생성 단계부터 제외했다:

- `H2H_SEASON_RECORD`("올해 상대전적 우위다?")와 `LAST_MATCHUP`("직전 맞대결
  스코어는?") 둘 다 어제(8/25) 실행이 오늘과 같은 5개 팀 조합으로 이미 냈던
  것과 결론·수치가 사실상 동일했다 — 상대전적 승패 누적이 하루 사이 1경기밖에
  안 바뀌어 "우위/열세" 결론이 그대로였고, "직전 맞대결"이 가리키는 경기 자체가
  바로 어제 그 경기라 `YESTERDAY_SCORE`·`WINNING_PITCHER`와 내용이 완전히
  겹쳤다(같은 경기를 세 가지 템플릿이 동시에 묻는 셈).
- `HOME_AWAY_SPLIT`·`RECENT_VS_EARLY`도 8/25 실행이 이미 사실상 전 구단(8~10개
  팀)을 훑은 상태라 오늘 새로 낼 신선한 팀이 거의 남지 않아 대부분 건너뛰었다
  (`RECENT_VS_EARLY`는 전 구단 소진으로 이번 실행에서 아예 0개).
- `STREAK_CURRENT`도 최근 7일 안에 같은 팀이 같은 구체적 연승/연패 수치로 이미
  나온 경우(NC 3연패, 두산 2연승, SK 1연승, 삼성/키움은 무승부라 연속기록 자체
  없음)는 제외하고, 값이 실제로 바뀐 팀(한화 1→2연패, KIA 6→1연승, 롯데
  3연승→2연패, LG 2연패→2연승, KT 1연승→1연패)만 남겼다.

**대응**: 경기 문항은 `YESTERDAY_WINNER`·`YESTERDAY_SCORE`·`WINNING_PITCHER`·
예측 5종(`PRED_*`)·`STREAK_CURRENT`(값이 바뀐 팀만)·선수 위키 소재
(`MEME_ORIGIN`·`RELATION_LINK`)로 물량을 채웠다 — 이 소재들은 대진이 반복돼도
매일 사실 자체가 갱신되거나(어제 경기·예측) 팀 귀속과 무관하게 새로 고를 수
있어(선수 700명+ 풀) 마르지 않는다. 결과적으로 경기당 EASY는 채웠지만
MEDIUM·HARD는 슬롯(10·5)에 크게 못 미쳤다(경기당 6개·1개 수준) — 공통 묶음도
`TEAM_RECORD_HISTORY`(역대 팀 기록 표가 크롤 포맷 문제로 파싱 불가)·
`TRENDING_WHO`(3회 연속 김도영 고정이라 스킵)를 제외해 EASY 슬롯이 특히 부족했다.

**제안**: 대진이 전날과 겹치는 날엔 애초에 `H2H_SEASON_RECORD`·`LAST_MATCHUP`을
① 템플릿 선택 단계에서 스킵 대상으로 결정적으로 판정하는 규칙을 두면(현재는
매 실행 이 세션이 최근 7일 원문을 일일이 대조해 판단해야 함), 판단 비용을 줄일
수 있다. `TEAM_RECORD_HISTORY`가 참조하는 `역대 팀 기록` 표는 `kbo-official.md`
렌더링이 팀명 헤더와 데이터 행이 어긋나 있어(연도별 표의 팀 순서와 실제 값 매칭
불가) 사람 검수 없이는 안전하게 못 쓴다 — py-collector 파서 쪽 확인이 필요하다.

## 30. H2H_SEASON_RECORD — 정답 보기에 팀명 노출 (2026-08-27 실행, 생성 단계에서 수정)

경기 묶음 서브에이전트 하나가 "올해 LG는 NC와의 상대전적에서 우위다?"라는

보기 문면에 팀명을 그대로 쓰지 않는다")을 위반했고 `validate_candidates.py`
check 9(정답 유출)에도 걸릴 뻔했다. 검증 단계에서 발견해 보기를
`{"A":"우위다","B":"열세다"}`로 고쳐 살렸다(evidence는 그대로 유효해 재작성이
아니라 보기 문구만 교체).

**교훈**: 같은 실행에서 다른 4개 병렬 서브에이전트는 전부 "우위다/열세다" 식
무팀명 보기를 정확히 지켰다 — 이 사례만 개별 편차. 다음 실행에서 이 템플릿
초안을 자체 점검할 때 "정답 보기에 `subject.teamCodes`의 팀 이름이 그대로
있는가?"를 생성 직후 자체 대조 항목으로 명시하면 이런 개별 편차를 생성
단계에서부터 줄일 수 있다.

맞는지"를 생성 직후 자체 검산하면 이런 결함을 걸러낼 수 있다.

## 33. 정적/준정적 사실 템플릿의 최근 7일 소진 — 검증 단계가 아니라 ①단계에서

이번 실행에서 raw candidate 73건 중 30건(41%)이 검증 패스 2단계(중복·편중
검사)에서 "최근 7일과 같은 사실"로 폐기됐다. 원인은 아래 템플릿들이
**"오늘 스냅샷"을 매일 새로 물어도 며칠 연속 답이 안 바뀌는 정적/준정적
데이터**를 다룬다는 데 있다:
  - `STREAK_CURRENT`·`HOME_AWAY_SPLIT`·`RECENT_VS_EARLY`: 시즌 흐름이
    안정적인 기간엔 "판단 방향"(연승/연패 지속, 홈이 강한지 등)이 며칠씩

  - `STANDINGS_NOW`(1위=KT 3주 연속 동일)·`STANDINGS_CLIMB`(SSG -6단계, 4/24

**제안**: ①템플릿 선택 단계에서 이 템플릿들을 고를 때, 최근 7일 이력에서
**같은 템플릿의 최근 답이 무엇이었는지**를 먼저 조회해 오늘도 같은 답이 예상되면
(예: 순위표가 최근 3일간 그대로) 애초에 후보에서 제외하는 규칙을 두면 좋겠다.
`MONTHLY_BEST`처럼 "완료된 달"을 묻는 템플릿은 한 달에 한 번만 내면 충분하므로
(이미 낸 달은 그 시즌 내내 다시 낼 필요가 없다), 최근 7일이 아니라 **이번
시즌 전체** 출제 이력과 대조하는 편이 맞다 — 대조 창을 템플릿 성격에 따라
다르게 두는 것도 검토할 만하다.

## 34. HOME_AWAY_SPLIT을 OX로 잘못 생성 — 카탈로그 format 미확인 (2026-08-29 실행, 생성 단계에서 발견·수정)

`HOME_AWAY_SPLIT`은 카탈로그에 `format: BINARY`로 선언돼 있는데, 생성 중
`STREAK_CURRENT`(OX)와 비슷한 "격차가 뚜렷하다?" 식 사실확인 문장이라
직관적으로 OX 보기(`O`/`X`)를 붙여 3건을 만들었다. `validate_candidates.py`

확인할 것(특히 BINARY와 OX는 문장 형태가 비슷해 헷갈리기 쉽다).

## 35. LAST_MATCHUP 오답 보기에 팀명 삽입 — 정답 유출 게이트 발견 (2026-08-29 실행, 생성 단계에서 발견·수정)

유출)에 정면으로 걸렸다("KT vs 삼성" 대상 문제인데 정답 보기에 "삼성"이
그대로 노출). "4:7, 원정팀 승"으로 팀명을 빼서 고쳤다 — `subject.gameId`가
이미 어느 매치업인지 특정하므로 보기에서 팀명을 빼도 정보 손실이 없다.

**교훈**: MATCHUP 스코프 문제는 "가독성을 높이려고" 보기에 팀명을 곁들이고
싶은 유혹이 특히 큰 유형이다(스코어만으로는 어느 팀이 이겼는지 바로 안
와닿아서) — 그 유혹 자체가 정답 유출 위험 신호임을 기억할 것. 질문 문면에는
팀명을 써도 되지만 보기에는 절대 안 된다는 경계선을 §11 규칙대로 지킬 것.

## 36. MILESTONE_FIRST/ALL_TIME_LEADER 오답 보기에 정답과 동일 인물 재등장 — chronological 카테고리 (2026-08-30 실행, 생성 단계에서 발견·수정)

`all-time-records.yaml`의 `rankBasis: chronological` 카테고리(예:
`history-player-hitter`)는 "그 부문 최초 달성자 순"이 아니라 "표의 행
순서"일 뿐이라 **같은 선수가 여러 rank에 중복 등장**할 수 있다(예: 장효조가
rank 2·4·5·6에 모두 등장). `MILESTONE_FIRST`에서 rank 5를 정답으로 뽑고
오답 보기를 "rank != 5인 다른 행"에서 기계적으로 채웠더니, rank 4의 이름이
정답(rank 5)과 **같은 인물**이라 보기에 같은 이름이 두 번 나오는 문제가
생겼다(정답 유일성 붕괴 — 어느 쪽을 골라도 사실상 정답). `validate_candidates.py`는
옵션 텍스트 중복을 별도로 검사하지 않아 이 결함을 못 걸렀다 — 생성 직후
`options` 텍스트 집합에 중복이 있는지 자체 점검해 잡아냈다. 오답 후보를
뽑을 때 "정답과 다른 rank"가 아니라 "정답과 다른 **이름**"으로 걸러야
한다(이름 기준 dedupe).

**교훈**: `all-time-records.yaml`처럼 한 인물이 여러 행에 걸쳐 반복 등장할
수 있는 자료에서 distractor를 뽑을 때는 반드시 이름 기준으로 정답을
제외하고 중복도 제거할 것 — rank/행 번호만으로 "다른 보기"라고 가정하면
안 된다. `validate_candidates.py`에 옵션 텍스트 중복 검사(check)를 추가하는
것도 검토할 만하다(현재는 생성 측의 자체 점검에만 의존).

## 37. TEAM_RECORD_HISTORY — kbo-official.md 표 헤더의 컬럼 오프셋 실수 (2026-08-30 실행, 생성 단계에서 발견·수정)

`역대 팀 기록` 섹션의 표 헤더는 `| {연도} | 경기 | 승 | 패 | 무 | 타율 |
평균자책점 | 승률 | {팀1} | {팀2} | ... |` 형태로, **연도 자체가 헤더 첫
컬럼**이다. 헤더 문자열을 `|`로 split한 뒤 "스탯 컬럼 7개(경기·승·패·무·
타율·평균자책점·승률)만큼 건너뛰면 팀명이 시작될 것"이라 보고 인덱스
7부터 팀명을 읽었더니, 연도 컬럼을 스탯 컬럼에 넣지 않은 것을 깜빡해
한 칸씩 밀려 **정답 보기에 "승률"(스탯 라벨)이 팀명 대신 들어가는** 결함이
생겼다(연도가 인덱스 0을 차지하므로 스탯 7개는 인덱스 1~7, 팀명은
인덱스 8부터). 업로드 전 각 후보의 `options[*].text`가 원본 표의 팀명
목록에 실제로 존재하는지 대조해 잡아냈다.

**교훈**: 렌더된 마크다운 표를 파싱해 옵션을 만들 때는 헤더 컬럼 인덱스를
"눈대중 오프셋"으로 계산하지 말고, 헤더 텍스트 자체에서 실제 팀명 패턴
(구단 풀네임 화이트리스트 등)을 찾아 위치를 확정할 것 — 인덱스 산수는
한 칸만 틀려도 결과가 조용히 틀린 값으로 채워져 결정적 검사망(형식 검사)을
빠져나가기 쉽다.

routine은 카탈로그·파서를 고치지 않으므로 이번엔 후보를 폐기하는 것으로 대응.

## 53. TEAM_RECORD_HISTORY — kbo-official.md "역대 팀 기록" 표의 헤더·행이 팀명으로 매핑되지 않아 과거 연도 evidence를 못 씀 (2026-09-12 실행, 버그 신고)

## 56. 카탈로그 `format` 선언을 직관으로 짐작하지 말 것 — H2H_SEASON_RECORD·HOME_AWAY_SPLIT은 OX가 아니라 BINARY (2026-09-13 실행)

카탈로그의 `format`도 OX라고 가정하면 안 된다. `validate_candidates.py`가
결정적으로 잡아내긴 하지만, 애초에 ③ 단계에서 맞춰 쓰면 검증 왕복이 줄어든다.

## 59. RECORD_OX — all-time-records.yaml 역대 레전드는 kboPlayerId가 없어 subject를 채우면 안 됨 (2026-09-14 실행)

금지)은 이 패턴을 못 잡는다 — YESTERDAY_WINNER류는 금지 템플릿
목록에 없고 애초에 "그 경기 자체·오늘 매치업에 관한 것만" 제약이
결정적 게이트가 아니라 프롬프트 설명에만 있었기 때문이다. **교훈**:
경기 유닛 프롬프트의 "최근 경기결과 바인딩" 지시에 "리그 전체가
아니라 이 두 팀이 **직접 등장하는** envelope만"이라는 제약을 더
명시적으로 강조할 필요가 있다 — "NC·한화가 등장하는 envelope 찾을

언급인지)가 불명확하게 해석될 여지가 있었다. 결정적 게이트에
"YESTERDAY_*·WINNING_PITCHER·LAST_MATCHUP·H2H_SEASON_RECORD류
템플릿의 top-level teamCodes 중 최소 하나가 evidence envelope의
entities.teamCodes와 겹쳐야 한다"는 검사를 추가하는 것을 다음
리뷰에서 검토할 것.

따라야 한다는 것을 암묵적으로만 전달하게 되는데, 일부 유닛이
